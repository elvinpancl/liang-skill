# liang-skill-maker：做 Skill，改 Skill

把一件反复要做、每次都得判断的事存成 Skill；或者把一个已有的 Skill 改到在真任务上站得住。新做和修改用同一套底线，流程轻重看活有多大。

## 三条底线

1. **先交方案，交完就停。** 只要会新建或改动 Skill 的文件，就先把打算怎么做写给用户，然后结束这一轮。交方案和写文件不放在同一轮回复里。活小，方案就短，一两行也算方案。
2. **没实际跑过任务，只说「查过结构」。** 报告用「验证等级」那一节的说法，做到哪级说哪级的话。
3. **只动说好的东西。** 动手前留好退路；用户自己没提交的改动、同名的旧目录不覆盖。发布、推送、装到别的宿主，每一样都要用户单独开口。

## 怎么向用户提问

- 问题直接写在回复正文里，编号列出，一次问完，然后结束这一轮。不用弹窗、选择题这类工具发问：换一种运行方式，它们可能到不了用户眼前。
- 从对话、文件、项目规则里查得到的，不问。
- 每个问题后面附一个建议答案和一句理由，用户回一句「都按建议」就能往下走。
- 项目或用户的全局规则要求少提问时，「新做」里的范围问题照样要问：它的答案在文件里查不到，又直接决定成品，只能由用户来定。

## 先分清这是哪一种活

| 用户带来的 | 这种活叫 | 怎么走 |
| --- | --- | --- |
| 一件想存下来的事；或者要把已有的 Skill 改名、拆开、合并、重写大半 | 新做 | 见「新做」，流程最全 |
| 一个出错的例子，或一句「不好用」「总是太啰嗦」 | 修 | 见「修」，先复现再动 |
| 说清了改哪一句、改成什么 | 小改 | 几行方案，确认就改 |
| 只要检查、诊断或测试 | 只看 | 直接交结果，不动文件，不用确认 |

拿不准算哪种，按重的那一档来，并在方案里说一声；用户可以要求降一档。

## 新做

**1. 看现场。** 读用户给的材料、目标目录和项目自己的规则文件（如 `AGENTS.md`、`CLAUDE.md`）。目标目录里已有同名 Skill 就停下来问。重写旧 Skill 时，把它现在已经做对的事列出来，改完要保住。

**2. 判断值不值得做成 Skill。** 按 [references/scoping.md](references/scoping.md) 的「四个去处」过一遍。更适合写成脚本、清单，或者根本不用存的，直接告诉用户，由用户决定还做不做。

**3. 写任务单，问范围，停第一次。** 先根据手头材料把任务单（格式见 scoping.md）能填的填上，再把填不上的攒成一组问题。下面三个范围问题每次都问：

- 它管哪几样东西？请把你平时会让它做的都列出来。
- 哪些挨着的事不归它管？
- 你平时会用什么话来叫它做这件事？

用户在开场白里举过的例子不算答完。例子只说明它至少管这些，没说明边界在哪。已经知道的部分写成「我的理解是……，还有别的吗」，再把你想到的近邻列出来让用户勾，例如他说了海报和活动页，就问自测页、头图要不要一起管。

同一条消息里再请用户选「先找现成做法」查多深（见下一步），给出建议。发出后结束这一轮，这一轮不交方案。

新做因此至少停两次：先停在问题上，再停在方案上。只有用户明说「别问了，直接出方案」，才能并成一次；这时把你替他定的范围在方案第 1 段里逐条列出，标明是你的假设。

**4. 先找现成的做法。** 不从零发明。按用户选的那一档做，细则见 [references/prior-art.md](references/prior-art.md)：

- **快查**：找两三个已经有人验证过的做法，再找一个常见但会出错的做法当反面。多数 Skill 用这档。
- **细查**：找四到六个结构相同的案例，成功的、失败的、反例都要有，列表对比。费时间，出错代价高的事才用。
- **不查**：做法已经在用户手里（自己的规范、已经跑顺的流程），直接往下走。

查完得到一副骨架：这件事分几步，每步靠什么判断。每个判断步骤写明依据是成熟做法、用户自己的经验，还是「凭经验，待验证」。写不出依据的步骤最容易时对时错，标出来，别装作有依据。

**5. 交方案，停第二次。** 下面六段都要有，小标题照这个写。缺了试几件和怎么退，不算交了方案。

```markdown
## 方案：新做 {名字}

1. 管什么，不管什么
2. 名字和简介（写出原文）
3. 文件夹里放什么：哪些写成话，哪些写成脚本，哪些放 references
4. 做法骨架：每一步和它的依据
5. 打算拿哪几件事来试，试几件，为什么是这个数
6. 写坏了怎么退回去

回「确认」我就动手。只想做其中几条，告诉我编号。
```

**6. 写。** 规矩见 [references/writing.md](references/writing.md)：名字、简介、正文、哪些该写成脚本。写完跑结构检查：

```bash
python3 scripts/check_skill.py <Skill 目录>
```

`python3` 找不到就换 `python`。两个都没有，照本文末尾的「手工检查」逐条过。

**7. 验。** 见 [references/testing.md](references/testing.md)。按活的大小定试几件事，简单的 1 件就够；不默认另开一批子会话来测。带着 Skill 和不带各跑一次，两边一样的部分从 Skill 里删掉。

**8. 报告。** 写清：Skill 叫什么、放在哪；管什么、不管什么；生成了哪些文件；验证到第几级，每件真事的结果；还没验证的地方；怎么叫它。最后提醒用户两件事：新装的 Skill 要新开对话才认得到；装的 Skill 多了，留意宿主有没有「简介被略掉」之类的超限提示。

## 修

**1. 看现场。** 读这个 Skill 的全部文件、已有的测试记录和项目规则，列出它现在做对的事。

**2. 复现，找到从哪一步开始偏。** 做法见 [references/fixing.md](references/fixing.md)：先拿到一次真实的出错，再分清是谁的错、错在哪一层。和 Skill 本身无关的（缺材料、环境坏了、偶尔一次），在方案里单独说明，不动 Skill。

**3. 交方案，然后停。** 五段都要有。

```markdown
## 方案：修改 {名字}

1. 出错的例子：实际怎样，本该怎样
2. 错在谁、错在哪一层
3. 改哪个文件的哪一处，改成什么；不改什么
4. 拿哪几件事验：原来出错的那件，加至少一件原来做对的
5. 改坏了怎么退回去

回「确认」我就动手。只想做其中几条，告诉我编号。
```

**4. 改，再对比。** 同一组任务，改之前的版本和改之后的版本各跑一遍，逐件比。结论三选一：留下、再试一轮、退回。整体变差就按退路恢复，并说明差在哪。

## 小改

交几行：改哪个文件哪一处、改成什么、不动什么、怎么退。确认后改，跑结构检查。这处改动会影响它怎么干活时，再拿 1 件事实际跑一次。

## 只看

直接交结果：结构检查的输出、读下来发现的问题、或者测试任务的实际表现。不动任何文件，所以不用等确认。用户看完想改，再按「修」或「小改」走。

## 什么算确认

- 算数的：「确认」「就按这个来」「只做第 2 条」「可以，名字别动」。这些话对得上眼前这一份方案。
- 不算数的：「帮我弄好」「你定吧」「尽快优化一下」。这是在托你办事，方案还没被看过。
- 用户确认时自己加了一条写得很清楚的改动，一并算数；需要你来判断怎么改的，先补进方案再问一次。
- 用户在讨论、在提问，或者没有回，就一直只读不写。

## 验证等级

| 等级 | 做到了什么 | 只许这么说 |
| --- | --- | --- |
| 1 查过结构 | 文件齐全，简介格式对，引用的文件都在，没有没写完的地方 | 「结构检查通过」 |
| 2 实际跑过 | 真的用这个 Skill 把至少 1 件事从头做完，看了结果，过关；修改时和改之前的结果比过 | 「实际试跑通过」，并写明材料是用户的真材料、示例，还是自己编的 |
| 3 换料也过 | 没参与设计的材料也过关，原来做对的事没有变差 | 「换材料和回归都通过」 |
| 4 别人装得上 | 换一台机器或另一个宿主，能装、能叫起来、资源都在 | 「安装验证通过」 |

没有实际跑过任务，就只能报第 1 级。第 2 级看的是有没有真的跑、结果过没过关：用示例材料跑通也算第 2 级，但要写明是示例，并提醒用户拿一件真事再跑一次。由动手修改的同一个会话自己试跑的，也在报告里注明。

## 手工检查

机器上没有 Python 时逐条看：

- `SKILL.md` 最上面有两行 `---` 夹着的一段，里面有 `name` 和 `description`。
- `name` 只有小写字母、数字和连字符，不超过 64 个字符，和文件夹名一样。
- `description` 不超过 1024 个字符，写了做什么、什么时候用、什么时候别用。
- 正文尽量在 500 行以内。
- 正文提到的每个文件都真的存在，都在这个 Skill 的文件夹里。
- `references/` 里的每个文件，正文都写了什么时候去读它。
- 没有没写完的地方，没有本机的私人路径、密钥和测试答案。

## 什么时候停

- 方案或问题已经发出，等用户回。
- 改完了，能做的验证都做了。
- 少一个会改变方案的决定，得用户来拿。
- 同一处已经补过一次还错：别再往上加规则，回到「修」的第 2 步看是不是更深一层的问题。
- 连着两轮看不出差别。
- 发现自己在按某一个例子打补丁。

## 发布

只在用户明确说要发布、分享、推到 GitHub 时才做。发布前查三样：有没有本机私人路径，有没有密钥或账号，有没有把测试答案带进去。推送、打标签、公开仓库这几步各自要用户点头。暂存时只加点名的文件。

## 改进本 Skill 自身

改的是 `liang-skill-maker` 自己时，先留一份改之前的副本当对照，验证时专门看两件事有没有被削弱：先交方案再动手；没实际跑过不报第 2 级。
