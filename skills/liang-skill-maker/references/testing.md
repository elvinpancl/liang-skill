# 验证一个 Skill

写方案里「拿哪几件事来试」那一段时，以及文件写完要验证时读这份。

## 试几件

按活的大小定，别一上来就摆开大阵仗。试跑要花时间和额度，试得多不等于做得好。

| 这次的活 | 试什么 |
| --- | --- |
| 小改，改的地方会影响它怎么干活 | 1 件能看出这处改动的真事 |
| 修 | 原来出错的那件；加至少 1 件原来做对的；有余力再加 1 件看着不同、毛病相同的 |
| 新做，事情简单、材料齐全 | 1 件最典型的真事 |
| 新做，事情复杂或出错代价高 | 3 到 6 件：典型的、缺材料的、挨着但不该它管的，再留 1 件不参与设计的 |

用来试的优先是用户真实的请求和材料。只有示例材料，或者只能自己编时，照样试，在报告里写明材料是哪一种。等级不因此降低，但要提醒用户拿一件真事再跑一次。

默认就在当前会话里试。另开子会话来测只在两种情况下用：用户要求；或者要做下面说的「不看答案」的测试。开了几个、花了多少，写进报告。

## 带和不带各跑一次

新做完的 Skill，拿同一句话、同一份材料跑两次：一次能用上这个 Skill，一次用不上。然后逐项比：

- **一边有、另一边没有的**，是这个 Skill 真正带来的东西。
- **两边一样的**，说明模型本来就会。把 Skill 里教这部分的文字删掉，留着只占地方。
- **带着反而更差的**，回去看是简介的事还是正文的事。

两边查出来的问题一样多，并不说明这个 Skill 白做了。它的用处可能在别处：每次交回来的样子一样，每条都带依据，该谁拿主意的事单列出来。把这一点写进报告，别硬说它「更准」。

记一笔时写清楚比的是什么。例：给「考勤补卡审核」这个 Skill 试跑，材料是 `runs/2026-03-08-buka-shenhe.md`，带着查出 7 处，不带也查出 7 处；差别是带着的那次每处都标了制度第几条，还单列了「补卡理由少于 9 个字，需主管定」。

## 哪一类 Skill 要定期重比

Skill 大致两类：

- **记自家规矩的**：公司的口径、规范、流程、哪些话不能说。模型再强也不会知道，长期有用。
- **帮模型补本事的**：教它怎么查错、怎么审方案、怎么拆问题。模型一升级，这些它可能自己就会了。

第二类做完时，在报告里提醒用户记下今天的日期，过一阵（比如模型换代以后）再做一次带和不带的对比。差不多了就让它退休。

## 测简介

简介管的是「它想不想得起来用」，和做得好不好是两回事，分开测。

- 准备一组话：两三句用户最常说的，一句说得很省的，都该用上它；一句挨着但不归它管的，一句完全无关的，都不该用上。
- 每句新开一个对话，不点名。看它有没有说要用这个 Skill，或者有没有去读它的 `SKILL.md`。
- 改了简介以后，拿同一组话再测一遍，改前改后放在一起看。只看「该用的用上了」不够，还要看「不该用的有没有被误叫起来」。

测出来「简介改得很烂也照样用上了」时，先别下结论，查两件事：宿主是不是因为 Skill 太多把简介全略掉了；是不是名字本身已经把用途说明白了。

## 不看答案

出错代价高、涉及安全或权限、准备公开发布、或者用户明确要求时，才做这种更严的测试：

- 留一两件材料，从头到尾不参与设计和修改，最后才拿出来跑。
- 执行测试的那一方只拿到 Skill 文件和测试用的那句话，不知道你改了什么、期望什么。
- 一件事十次里九次做得漂亮、一次把事实写错，按「有严重问题」算，不拿平均分盖过去。

## 写东西的 Skill 怎么打磨

让它「按我的风格写」这一类，对错没有标准答案，要靠用户亲手改出来。

1. 让它照着 Skill 写一版。
2. 用户亲手把这一版改成自己满意的样子。只说「不够好」不算，要真的动笔改。
3. 把两版都交回来，逐处比差在哪，把差别归成几条写回 Skill。
4. 转三四轮就停。再多，它会越来越贴合改过的那几篇，换个题目反而写不好。

开始之前先把样本分堆：不同时期、不同平台、不同用途的稿子各归各的，一次只拿一堆来学。混在一起学到的是平均数，哪种都不像。两篇样本口气像、讲道理的路数不像时，以路数为准。

文风、审美、策略好不好，把关键差别的原文摆给用户看，由用户判断，不要用机械的打分代替。

## 报告里写什么

- 验证到第几级（等级表在 `SKILL.md`）。
- 每件试跑的事：用的什么材料，结果怎样；修改时写改前改后各怎样。
- 带和不带的对比结果，以及据此删掉了什么。
- 是谁试的：当前会话自己试的要注明，这种结论要打些折扣。
- 还没验证的地方。
