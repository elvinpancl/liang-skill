# 修一个已有的 Skill

用户带着出错的例子，或者只有一句「不好用」来找你时读这份。已经说清改哪里、改成什么的小改，不用读。

先记住一件事：Skill 不会越用越好。它是一堆文件，每一次变好，都是因为有人把运行结果拿回来、改了文件并保存。这次不写进文件，下次它还是老样子。

## 先拿到一次真的出错

- 用户给了出错的输出或运行记录：整份读完，找出是从哪一步开始偏的。只看最后的答案容易怪错地方。
- 用户只有印象，比如「它总是太啰嗦」：拿一句贴近平时用法的话把当前版本跑一次，拿到实际输出。
- 跑不了，也没有记录：在方案里把这条标成「没复现」，对应的改动写成待验证的猜测。

「更聪明」「更像我」这类目标，先翻成看得见的行为再动手。比如「没核实的事别急着下结论」可以翻成：认得出哪些说法没核实，给它们打上标记，提出去哪核实，不写肯定的结论。

## 先分清是谁的错

| 现象 | 是谁的事 | 怎么办 |
| --- | --- | --- |
| 该用的时候没用，不该用的时候跑出来 | 简介 | 改简介，正文不动 |
| 同一步每次都错 | 正文 | 往下看错在哪一层 |
| 缺了会改变结论的材料 | 材料 | 补材料，或者让它在缺的时候先问 |
| 测试题自己前后矛盾，或者期望的答案本身不对 | 测试题 | 改测试题，Skill 不动 |
| 没权限、断网、文件不在、依赖没装 | 环境 | 修环境，Skill 不动 |
| 同样的条件偶尔错一次，找不出规律 | 运气 | 先不改，多跑两次再看 |

只有前两种会进修改清单。后四种在方案里单独交代，不要顺手改 Skill。

## 正文的错，再看是哪一层

| 层 | 长什么样 | 怎么修 |
| --- | --- | --- |
| 话没写清 | 条件没写明，或者两条规矩互相打架 | 补上条件，删掉打架的那条 |
| 这一步没有靠谱的办法 | 这一步全靠模型临场发挥，所以时对时错；或者用的办法本来就不对路 | 给这一步换一个判断的办法，依据见 [prior-art.md](prior-art.md) |
| 整条路不对 | 换哪一步都救不回来 | 告诉用户，建议按「新做」重来，由用户决定 |

改在能把这一类错都解释掉的那一层。怎么判断：同一个地方已经补过一次规矩还在错，多半就不在第一层了，别再往上加规矩。

## 改的先后

每处改动先写一行：看到了什么错，猜是什么原因，改哪里，指望改善什么，可能碰坏什么。然后按这个先后选改法，靠前的优先：

1. 把「什么情况下做」「做到什么时候停」补清楚。
2. 调整步骤的先后，或者上一步交给下一步的东西。
3. 加一个能把错拦下来的检查点。
4. 把重复、死板的那部分挪进脚本。
5. 删掉没用的和互相打架的话。
6. 实在不行，才加一条新规矩。

新加的规矩要说得出它管哪一类错。别把测试题的答案、某个专有名词、某一个例子的细节直接写成通用规矩。

## 看着像变好，其实没有

碰到下面任何一种，都不能算改好了：

- 追着一条反馈改，把一次的口味写成了永远的规矩。
- 只加不删，文件越来越长，前面和后面开始打架。
- 反复拿同一组例子来试，它慢慢学会了讨好这几个例子。
- 试跑的一方事先知道期望的答案。
- 十次里九次不错，剩下一次把事实、权限或安全上的事做错了，却按平均分报喜。
- 只看到「该用的时候用上了」，没查它有没有在不该用的时候被叫起来。

## 改完怎么比

同一组任务，改之前的版本和改之后的版本各跑一遍，输入、权限、模型都保持一样。改之前的版本从 Git 的上一次提交拿，或者动手前先存一份副本。逐件记下改前改后各做到了什么，把关键差别的原文摆给用户。

结论三选一：

- **留下**：出错的那件好了，原来做对的没变差。
- **再试一轮**：有改善，但不稳，或者碰坏了别的。
- **退回**：整体变差。按退路恢复，说明差在哪。

连着两轮看不出差别就停，把现状和还没解决的问题告诉用户。

## 要不要留记录

用户打算长期养这个 Skill，或者这一轮做了「不看答案」的测试，就在 Skill 的 `evals/` 目录（或用户指定的地方）记一笔：这轮想解决什么，用了哪些材料，改了什么，改前改后各怎样，还剩什么没解决。写到下一次接手的人看了能接上。改一句话的小活不用记，报告里说清就行。
