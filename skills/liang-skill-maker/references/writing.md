# 写 Skill 文件的规矩

方案确认以后、动手写文件时读这份。

## 文件夹里放什么

只有 `SKILL.md` 是必须的，别的用得上再加。

| 放什么 | 放哪 | 什么时候加 |
| --- | --- | --- |
| 名字、简介、做法 | `SKILL.md` | 必须有 |
| 做到某一步才要翻的规则、标准、例子 | `references/` | 正文超过三百来行，或者某段内容只有少数情况用得上 |
| 每次都一样、要跑得准的操作 | `scripts/` | 这部分规则能写死 |
| 要原样拷进成品的模板、图片、字体 | `assets/` | 成品里真的用得到 |
| 宿主界面上显示的名字和默认提示 | `agents/openai.yaml` | 在 Codex 里用，想让它在列表里好认 |

文件名用英文小写加连字符。中文文件名在 Windows 上解压、拷贝时容易变成乱码。

## 名字

名字要让人一眼看出它管什么，`poster-design` 比 `helper-2` 强。这一条比看上去要紧：装的 Skill 多了，有的宿主会把所有简介整个略掉，目录里每个 Skill 只剩名字和文件位置，这时它只能凭名字挑。

- 只用小写字母、数字和连字符，不超过 64 个字符。
- 文件夹名和 `name` 一样。
- 团队或个人的一组 Skill 用同一个前缀，方便辨认。

## 简介

简介是 Agent 决定用不用它的依据。写三样，按这个顺序：

1. **做什么。** 头一句写最要紧的，简介被截短时它还在。
2. **什么时候用。** 把用户平时开口的原话写进去两三句。
3. **什么时候别用。** 写出最容易和它撞车的那一两件事。

别用「我」「你」，直接写它做什么。整段不超过 1024 个字符，三百字以内最好。不往简介里塞做法细节，那是正文的事。

和另一个 Skill 老是抢活时，两边的简介各补一句「不管什么」。

## 正文

- 只写模型自己不会知道的东西：你们的规矩、这件事的先后、做到什么程度算完、什么情况要停下来问。通用常识、空话口号不写。
- 用祈使句直接说做什么。每一步写清输入是什么、交出什么、什么情况下停。
- 需要用户拿主意的地方，写明「停下来等用户」；不需要的地方别制造问答。
- 引用 `references/` 里的文件时，同一句话里写清什么时候去读它。只在某一步才用的资料，到那一步再读。
- 尽量在 500 行以内。超了先看有没有能挪进 `references/` 的大段内容。
- 例子用来说明规则，别把某一个例子的答案当规则写进去。

## 写死的和要判断的分开

同一个 Skill 里常常两样都有。

- **每次都一样的，写成脚本。** 格式转换、重命名、校验、按固定规格排版。脚本运行时不占对话的地方，只有结果会回到对话里。脚本只用标准库，写明怎么运行，写完要真的跑一次。
- **每次要看情况的，写成话。** 只写分寸和边界，具体怎么判断交给模型。例如「每节标两到四处重点，标了重点的段落不超过全篇三成」，不必写「第一句一定标」。

## 宿主放不放得下

写完提醒用户看一眼：

- 新装的 Skill 要新开一个对话才认得到。
- 装的 Skill 很多时，留意宿主启动时有没有超限的提示。Codex 的原话是 `Exceeded skills context budget. All skill descriptions were removed`。出现这类提示，说明简介已经不起作用，这时候要么删掉不用的 Skill，要么确保名字足够好认。

## 交出去之前

- 简介能和最像它的那个 Skill 分得开。
- 正文提到的文件都在，都在这个 Skill 的文件夹里。
- 脚本跑过。
- 没有本机的私人路径、密钥、账号，没有测试题的答案。
- 没有留着没写完的段落。
- 项目自己有校验脚本的，也跑一遍。
