# 值不值得做成 Skill，以及任务单怎么写

新做一个 Skill、用户手里只有一个想法或一句「帮我存一下」时读这份。读完要回答两件事：这件事该不该做成 Skill；如果该，它到底管什么。

## 四个去处

一件反复做的事，先看它该去哪，Skill 只是其中之一。

| 这件事的样子 | 去处 | 怎么跟用户说 |
| --- | --- | --- |
| 规则能写死，同样的输入永远得到同样的输出 | 写成脚本 | 「这件事每次都一样，写成程序直接运行更稳，不用做成 Skill」 |
| 主要是怕漏项，几乎不用判断 | 清单或模板 | 「一张清单就够了」 |
| 做法大致固定，但每次都要看材料下判断，以后还会再来 | 做成 Skill | 往下走 |
| 只做这一次，或者每次都靠临场决定、归纳不出做法 | 不存 | 「这次直接做，等它再出现一两回再说」 |

一件事常常两样都有。这时拆开：写死的那部分放进 Skill 的 `scripts/`，要判断的那部分写成正文里的话。比如排版，字号颜色是死的，挑哪几句加粗是活的。

## 值得存的四个条件

- **做过不止一回。** 拿得出至少两次真实发生的例子。只有一次的，先把这次做顺。
- **进来的和交出去的都稳。** 每次给它的材料差不多，做完的东西长得也差不多。
- **看得出对错。** 能指着结果说哪里不对。只说得出「感觉不好」的，先帮用户把「不好」说成看得见的东西。
- **管的事说得清。** 说得出它管什么、不管什么。

四条不全满足时，把范围收窄，只存稳的那一段。别为了一个例子写一套规矩。

## 任务单

先自己填，填不上的才去问。

```markdown
## 任务单

这件事什么时候会出现：
现在怎么做，卡在哪：
做成 Skill 以后要交出什么：
它管的东西（逐样列出）：
挨着但不归它管的事：
用户平时怎么开口叫它：
拿什么证明做对了：
还没弄清、先当假设的：
```

「拿什么证明做对了」只写看得见的：一个文件、一张表、一个动作、一句明确的结论。「更专业」「更像我」这类说法要先翻成看得见的行为，翻不出来就问用户要一个他满意的例子和一个不满意的例子。

## 范围问题怎么问

三个问题每次都问，原因是它们最容易被跳过，后果又最难看：一个只做了海报的 Skill，用户转头让它做活动页，它要么不动，要么乱做。

1. **它管哪几样？** 请用户把平时会让它做的都列出来。用户只举了一个例子时，追一句「还有别的同类的东西吗」。
2. **哪些挨着的事不归它管？** 把你想到的近邻列给用户勾选，比在空白处让他想要快。
3. **平时怎么开口？** 要原话，两三句就行。它们会直接写进简介。

问的时候附上你的建议答案。例如：

```text
1. 它管哪几样？我看到你提了讲座海报和活动页。自测页、公众号头图要不要一起管？
   建议：海报、活动页、自测页一起管，它们用的是同一份规范。
2. 哪些不归它管？建议：写文案、改活动信息不归它，它只管长什么样。
3. 你平时怎么开口？建议先按「做张海报」「做个活动页」写，你有别的说法告诉我。
```

## 什么时候可以往下走

- 下一步该做什么已经确定。
- 它交出的东西长什么样已经确定。
- 用户或者测试的人看得出它做没做完。
- 剩下没弄清的事，不会改变它的主要结构。
