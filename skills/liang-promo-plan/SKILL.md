# liang-promo-plan：品宣视频拍前规划

品宣片是拍给没用过的人看产品能做什么，不是拍给研发看它怎么做到的。 `[待验证]`

公开版提供产品品宣拆集、贯穿案例与录屏清单的方法。客户资料、实际项目规划与反馈记录不随 Skill 发布；完成后的效果需要在使用者自己的项目中检验。

## 适用范围

- 处理：品宣视频系列的拆集、贯穿案例、演示数据清单、录屏清单和开录前准备。
- 不处理：
  - 录完以后的核对和配图，走 liang-promo-footage。
  - 写文章，走 liang-promo-article。
  - 剪辑台本、粗剪和配音字幕稿，走 liang-promo-edit；精剪在剪辑软件里做。
  - 短视频内容闭环的选题，走 liang-content。
- 缺产品资料，也没有后台可看：暂停，只问「有没有产品资料，或者可以只读浏览的后台」。
- 缺受众：默认是有技术背景、但没用过这个产品的人，在计划里写明这个假设。

## 公理

### 公理 1：每集只回答三个问题 `[待验证]`

- 方法依据：方法假设：每集集中回答能做什么、省掉什么麻烦、大概怎么用。
  - 原理、架构、参数、配置细节都不讲。
  - 深度功能能自然出现在主流程里，就带一句，融不进就不提。
  - 用户点名把某个深度能力升为重点时照样展示，只是用大白话和真实界面讲。
- 反例：受众是来做技术选型的研发团队，要的就是架构。那是技术分享，不是品宣片。
- 复核：试看时问观众这集展示了什么能力，答不上来就是拆错了。

### 公理 2：一个贯穿案例，全部用模拟数据 `[待验证]`

- 方法依据：方法假设：用单一、虚构的贯穿案例帮助观众理解完整业务链。
  - 案例选观众一听就懂的业务，例如售后客服。
  - 演示数据全部模拟，所以不用考虑商用授权。商品可以用真实品牌型号，更有真实感。
  - 只拍产品里的操作，外部服务一句带过，能证明接得进来就够了。
- 反例：产品已经有可以公开的真实客户案例时，真实数据（脱敏后）更有说服力。
- 复核：试看时，观众能不能复述这个案例在每集里干了什么。

### 公理 3：多身份产品，每个镜头写明身份 `[待验证]`

- 方法依据：方法假设：每个镜头写明操作身份，避免不同角色的页面和权限混淆。
- 反例：只有一个身份的产品不用写。
- 复核：录完对照时，看身份一列有没有判断不出来的镜头。

### 公理 4：只列在产品里亲眼看到的页面 `[待验证]`

- 方法依据：核验原则：只把亲眼见到的页面列成已核实镜头；由代码、语言包或接口推测的页面标「待核实」。
- 反例：无。
- 复核：每次规划结束，检查有没有标「待核实」的页面被列成了正式镜头。

### 公理 5：补元素时插回原来的顺序，不重排结构 `[待验证]`

- 方法依据：方法假设：在既定结构中补充镜头，并标注新增项，减少无关重排。
- 反例：系列结构本身被用户推翻时，整体重排。
- 复核：交付清单时，看用户还能不能一眼找到原来那几集。

## Phase 1：取材

钉子台词：「先看产品里到底有什么，再说拍什么。」

- 输入：产品资料（PPT、官网、手册），以及用户登录好的线上后台。
- 动作：
  1. 从资料里摘出能力分层、痛点说法和卖点原话，写品宣时沿用。
  2. 只读浏览后台：只看不改，不点保存、创建、删除、发布。登录和凭据由用户自己输入。用宿主可用的浏览工具。
  3. 做页面盘点表，每页写页面、路径、看到了什么、有没有数据，状态标「看到」「有数据」「待核实」三种之一。
- 退出：主链路上每个要拍的能力都有对应页面，状态明确。
- 暂停：需要登录或切换账号时，请用户操作。

## Phase 2：拆集

钉子台词：「一集一个能力，三分钟里要看到结果。」

- 输入：页面盘点表、资料里的能力分层。
- 动作：
  1. 选拆法：按能力层拆（例如构建、生态、管理），或者按主链路拆（准备、资料、助手、工具、任务、交付、共享）。不按后台菜单拆。
  2. 每集写四项：观众问题、画面里要出现的结果、涉及的页面、前置条件。
  3. 用三条检验每一集，任何一条不满足就和相邻一集合并：
     - 能写出一句观众问题。
     - 三分钟内能出结果。
     - 前置条件十秒说得清。
  4. 画系列地图，标出每集在链路上的位置。格式见 [references/录屏清单模板.md](references/录屏清单模板.md)。
  5. 按 liang-promo-edit 的可调默认参数初估时长，并标明这是待校准预算。拍前只写段落和观众问题；逐句旁白在粗剪后结合画面编写。
- 退出：系列地图，以及每集一行的清单。
- 暂停：系列地图交用户确认。用户说先做加法时，把元素全列进来、标成候选，减法留到录完以后再做。

## Phase 3：贯穿案例与演示数据

钉子台词：「案例一听就懂，数据全是模拟的。」

- 输入：系列地图。
- 动作：
  1. 定案例：观众一听就懂，能串起所有集的业务场景。
  2. 按镜头列演示数据，包括资料卡、样例订单、提示词、技能定义、账号。每一项写清给哪个镜头用、谁来准备。
  3. 录之前把资料过一遍，确认互相不矛盾，例如同一个时效不能写成两个数。
- 退出：演示数据清单，每一项都对得上镜头。
- 暂停：不暂停。

## Phase 4：录屏清单

钉子台词：「每个镜头写清谁在操作、要拍到什么结果。」

- 输入：系列地图、演示数据清单。
- 动作：
  1. 每集一张镜头表，列为镜头号、身份、页面、操作、画面里要出现的结果、标注。标注写「新增」「可选」或「不录」。
  2. 写开录前统一准备：
     - 身份表：每个身份用哪个账号、在画面上怎么认出来。
     - 浏览器窗口和缩放比例固定，关掉公告条，统一主题和语言。
     - 敏感信息录屏时不用刻意回避，剪辑时统一打码。
  3. 破坏性操作（删除、清空、停用）默认不录，标「不录，口播带过」。
  4. 按公理 5 补元素：插回原来那一集的顺序里，标「新增」。
- 退出：每集的镜头表齐全，每个镜头都有身份和预期结果。
- 暂停：清单交用户确认以后再开录。

## Phase 5：交接

录完以后，把下面这段交给 liang-promo-footage：

```yaml
liang_handoff:
  from: liang-promo-plan
  shot_list: <录屏清单路径>
  roles: [<身份 1，以及怎么从画面认出来>, <身份 2>]
  footage_dir: <原片目录，录完再填>
  evidence_level: 待验证
  next: liang-promo-footage
```

取证那边会在清单每集末尾追加「实录对照」，不改原计划行。

## Refusals

- **「把这个功能的原理和架构也讲讲」** → 拒绝在品宣片里讲原理。观众是来看产品能做什么的，原理会把能力淹没。改成一句大白话说明用途，要深讲就另做技术分享。
- **「语言包里有这个页面，也列进去」** → 拒绝列成镜头。只在文案里出现的页面可能根本不存在。先标「待核实」，在产品里看到再列。
- **「演示一下删除」** → 默认不录破坏性操作。录屏用的是真实环境，删掉的东西可能收不回来。在清单里标「不录，口播带过」；用户坚持要录，就用专门准备的演示数据。

## 产出位置

- 制作计划和录屏清单是成品，放项目目录顶层，按项目约定命名。
- 演示数据放 `演示资料/`。
- 浏览截图、页面盘点草稿这类过程文件放 `制作过程/`。

## 验证契约

- **静态检查**：
  - 清单里每个镜头都有身份和预期结果。
  - 没有标「待核实」的页面被列成正式镜头。
  - 破坏性操作都标了不录。
- **公开证据边界**：发布包不包含客户项目原始证据。运行自测只能验证合成样例和脚本边界，真实项目效果需单独核验。
